# DataLoader audit and stabilization, October 2026

**Scope.** A review of DataLoader 1.0 (`cd6354e`, GitHub `main` on
2026-10-15) against its goals: a reusable, config-driven acquisition front
end for eMapR pipelines; USGS ARD as the preferred Landsat source with
Planetary Computer, Earth Search and (planned) Copernicus as alternatives;
scientifically exact handling of source data; outputs another pipeline can
consume without knowing DataLoader's internals. The fixes are on branch
`stabilize` (DataLoader 1.1.0). The Oregon archive download was left
running untouched throughout.

**Verdict.** The foundation is sound: one engine for every request shape,
strict configs, atomic and resumable writes, and an Oregon archive whose
sampled pixels, band mapping, grid and checksums are correct. The audit
found one silent data-loss bug (Sentinel-2 on Planetary Computer), gaps in
the output contract that a downstream pipeline would have tripped on, no
protection against outages using up retry attempts, and documentation that
understated the archive's cost. Those are fixed below. The main open items
are a live one-tile check of the new USGS checksum verification, the cause
of the Oregon run's memory peak, and two suspected scale/fill issues in
providers eMapR doesn't use today (GLAD, GEE).

## For users of 1.0 configs

- Configs using `glad_ard`, or `gee` for Sentinel-2, must add
  `sensors[].product_family` (`glad_ard`, `esa_s2_l2a_harmonized`).
- USGS credentials in `provider_options` are rejected: use
  `USGS_M2M_USERNAME`/`USGS_M2M_TOKEN`.
- New exit code 5: the run stopped itself; fix the cause and re-run.
- 1.0 datasets are read and resumed as they are.

## Migrating the Oregon archive

Approved 2026-10-15; not done yet. Nothing touches imagery, and nothing
happens while the current download runs.

1. Let the running download finish (`RUN_EXIT=` in its log). It holds the
   dataset lock and the only USGS M2M account, and rewrites `manifest.json`
   and `items.jsonl` every 10 minutes.
2. Live check of 1.1 in a scratch directory: a small `usgs_ard`
   acquisition, confirming the SHA-512 verification against real USGS
   files. The migration stops here if it fails.
3. Back up `manifest.json` and `items.jsonl` (0.13 GB).
4. `data-loader upgrade /vol/v1/data/oregon_landsat_ard --check-files 50
   --run 2026-10-07T18:47:00Z=1f14cda… --run 2026-10-08T03:13:22Z=5fd1970…`
   (12 s on a copy of today's metadata). Adds per-file scale/offset, QA
   nodata, per-row software from the two runs, the run history, and the
   resolved `product_family`.
5. Verify: acquisition counts unchanged; every acquired file has per-band
   scale/offset; QA nodata; every row attributed to a run; sampled files
   agree with the metadata.
6. Resume with 1.1 (same command as before) to retry the last failures
   and add acquisitions published since 2026-10-07 (2–5 per finished
   tile as of 2026-10-15). Existing imagery is not downloaded again.

Verified on a copy of the live metadata: counts unchanged; all 75,907
acquired files got per-band scale/offset; 3,449 + 72,458 rows attributed;
20 sampled files' GDAL scale/offset/nodata agree; running it twice is a
no-op; `plan` with the pinned example config matches every acquired item.
